# MRMAC 1x40GE reference (Versal AI Edge, xcve2202)

Reference for the single 40GBASE-R4 (XLAUI-4) configuration of the MRMAC,
captured from the AMD example design generated by Vivado 2025.2. It is the
source for the 1x40G mode of the Corundum Versal glue. Items identical to the
1x100GE or 4x25GE designs are only stated briefly; see
`mrmac_4x25g_reference.md` for the full clock/reset analysis.

## How the reference was generated

`create_ip -name mrmac` on `xcve2202-sfva784-1MP-i-S` with:

    MRMAC_PRESET_C0 {1x40GE XLAUI-4 Wide}   MRMAC_MODE_C0 {MAC+PCS}
    GT_TYPE_C0 GTYP                         GT_REF_CLK_FREQ_C0 156.25

then `generate_target all` and `open_example_project`. Properties read back
from the generated xci: `MAC_PORT0_RATE_C0 = 40GE`,
`MRMAC_DATA_PATH_INTERFACE_PORT0_C0 = Independent 256b Non-Segmented`
(PORT2 reads `Independent 32b  Non-Segmented` and PORT1/PORT3 `N/A`, a preset
artifact; port 0 is the only 40G port), `TIMESTAMP_CLK_PERIOD_NS = 4.0`
(250 MHz), `MRMAC_EXDES_GT_LOCATION_C0 = GTYP_QUAD_X0Y1`,
`MRMAC_EXDES_GT_REFCLK_LOCATION_C0 = GTYP_REFCLK_X0Y2` (`mrmac_0.xci`).

Citations use these example-design files (kept in the generation scratch
area, not in the repo). Names are as generated for the IP name `mrmac_0`:

- `E` = `imports/mrmac_0_exdes.sv`
- `T` = `imports/mrmac_0_exdes_tb.v`
- `C` = `mrmac_exdes_test.c`, `test_40GE()` (C:753-868)
- `G` = `mrmac_exdes_gt_settings.tcl` (gtwiz_versal configuration)
- `X` = `mrmac_0_ex.srcs/sources_1/ip/mrmac_0_gtwiz_versal/mrmac_0_gtwiz_versal.xci`
- `M` = `imports/mrmac_0_gen_mon_all.sv` (traffic generator/monitor)
- `D` = `imports/mrmac_0_example_top.xdc`

## gtwiz_versal configuration

G sets `INTF0_GT_SETTINGS` and not `NO_OF_INTERFACE` (one interface), with one
interface of four lanes (`INTF0_NO_OF_LANES 4`, `QUAD0_PROT0_LANES 4`, X):

    LR0_SETTINGS {preset GTYP-Ethernet_10G_RAW RXPROGDIV_FREQ_VAL 644.531
                  RX_REFCLK_FREQUENCY 156.25 TXPROGDIV_FREQ_VAL 644.531
                  TX_REFCLK_FREQUENCY 156.25}                       (G:5)

The preset expands (read back from the resolved INTF0 settings in X) to:

| Field | Value |
|---|---|
| `PRESET` / `INTERNAL_PRESET` | `GTYP-Ethernet_10G_RAW` / `Ethernet_10G_RAW` |
| `TX_LINE_RATE` / `RX_LINE_RATE` | 10.3125 Gb/s per lane |
| `TX_DATA_ENCODING` / `RX_DATA_DECODING` | RAW |
| `TX_USER_DATA_WIDTH` / `RX_USER_DATA_WIDTH` | 32 |
| `TX_INT_DATA_WIDTH` / `RX_INT_DATA_WIDTH` | 32 |
| `TX_PLL_TYPE` / `RX_PLL_TYPE` | LCPLL |
| `TX_REFCLK_FREQUENCY` / `RX_REFCLK_FREQUENCY` | 156.25 |
| `TX_REFCLK_SOURCE` | R0 |
| `TXPROGDIV_FREQ_VAL` / `RXPROGDIV_FREQ_VAL` | 644.531 (source LCPLL, enabled) |
| `TX_OUTCLK_SOURCE` / `RX_OUTCLK_SOURCE` | TXPROGDIVCLK / RXPROGDIVCLK |
| `TX_BUFFER_MODE` / `RX_BUFFER_MODE` | 1 |

Per lane the user data is 32 bits, so one 256b MRMAC word is carried by four
32b lanes; the 40GE user clock is 10.3125 Gb/s / 32 = 322.265625 MHz. The
PROGDIV 644.531 MHz is the outclk fed to MBUFG_GT; its O2 output is the fixed
/2 tap (322.266 MHz), as in the 25G reference.

The remaining G properties are not rate specific and match the 4x25GE example:
`ENABLE_REG_INTERFACE true`, `REG_CONF_INTF AXI_LITE`, `QUAD0_GT_GPIO_EN true`,
`QUAD0_CH[0-3]_LOOPBACK_EN true`, `QUAD0_{TX,RX}[1-3]_OUTCLK_EN true` (G:4-17).
Compared with the existing 1x100GE build (`corundum_vck190_mac.tcl`) only the
preset, line rate (25.78125 -> 10.3125), and data widths (80 -> 32) change;
the lane count, protocol count and `LCPLL` PLL type are the same.

## Clocks

The example uses the same structure as 1x100GE: one TX MBUFG_GT off lane 0
(`mrmac_0_mbufg_gt_0`, input `gt_quad_base_ch0_txoutclk`, E:1615-1633) and one
RX MBUFG_GT per lane (inputs `gt_quad_base_ch[0-3]_rxoutclk`, E:1645-1730).
All are `MODE("PERFORMANCE")`, `CE=1`, `CEMASK=0`, `CLRMASK=0`, `DIV=3'b000`,
`O3/O4` open, CLR/CLRB_LEAF from `INTF0_{TX,RX}_clr_out`/`_clrb_leaf_out`
(E:1501-1504).

| MRMAC pin | Source | Example line |
|---|---|---|
| `tx_core_clk[3:0]` | TX MBUFG_GT **O1**, lane 0, replicated | E:801 |
| `rx_core_clk[n]`, `rx_serdes_clk[n]` | RX MBUFG_GT n **O1** | E:799-800 |
| `tx_alt_serdes_clk[3:0]` | TX MBUFG_GT lane 0 **O2**, replicated | E:803 |
| `rx_alt_serdes_clk[n]` | RX MBUFG_GT n **O2** | E:802 |
| `tx_axi_clk[3:0]`, `rx_axi_clk[3:0]` | one clk_wiz output (`tx_axi_clk_mmcm`), all bits and both directions | E:791-794, E:818-819 |
| `tx_ts_clk`, `rx_ts_clk` | one 250 MHz clk_wiz output (`ts_clk`) | E:805-806; `mrmac_0_exdes_imp_top.sv:147-149` |
| `s_axi_aclk` | 100 MHz `pl0_ref_clk_0` | `mrmac_0_exdes_imp_top.sv:212` |

- The example AXIS clock is **390.625 MHz**: `mrmac_0_axis_clk_wiz_0` takes
  the 100 MHz `pl_clk` (`PRIM_IN_FREQ 100`) and has
  `CLKOUT_REQUESTED_OUT_FREQUENCY 390.625` on output 1 (E:791-794;
  `mrmac_0_axis_clk_wiz_0.xci`). This is the same wizard output as for 100GE
  and 4x25GE. MODE_REG `ctl_axis_cfg` is 101 (below), the same as 100GE.
- The gtwiz `QUAD0_TX[0-3]_usrclk` inputs are all the TX O2 net
  (`MBUFG_GT_tx_usrclk2_0`) and `QUAD0_RX[n]_usrclk` the RX O2 of lane n
  (E:1568-1575), i.e. O2 -> gtwiz usrclk and alt_serdes, O1 -> core/serdes,
  as in the 100G glue.
- **GTREFCLK1 is not used.** One `IBUFDS_GTE5` (`REFCLK_EN_TX_PATH 0`,
  `REFCLK_HROW_CK_SEL 0`, `REFCLK_ICNTL_RX 0`) drives only `QUAD0_GTREFCLK0`
  (E:1731-1745, E:1465). `QUAD0_GTREFCLK1` is declared (E:1235) but neither
  driven nor connected. This differs from the 4x25GE example, which feeds both.
  Constraint: `create_clock -period 6.400` on `gt_ref_clk_p` (D:65).
- **The alt-serdes clocks are used**: `tx_alt_serdes_clk` and
  `rx_alt_serdes_clk` are driven from the O2 outputs (E:802-803). The flexif
  clocks are tied to `4'b0000` (E:765-766).
- There is no `tx_serdes_clk` pin connected (same as 100G/25G).

## MRMAC register program (`test_40GE()`)

Single port, base 0. In order (C:753-868):

| Step | Write | Line |
|---|---|---|
| RESET_REG assert | `RESET_REG_0 = 0xFFFFFFFF` (T: `0xFFF`, T:540) | C:778 |
| MODE_REG | `MODE_REG_0 = 0x40000A42` (T:542) | C:781 |
| CONFIGURATION_RX_REG1 | `0x00000033` | C:786 (T:544) |
| CONFIGURATION_TX_REG1 | `0x00000C03` (T:546) | C:787 |
| FEC_CONFIGURATION_REG1 | `FEC_CONFIGURATION_REG1_0 = 0x00000000` (T:548) | C:788 |
| RESET_REG release | `RESET_REG_0 = 0` (T:553) | C:789 |
| GT reset/line rate | `GT_LINERATE_RESET = 0x00001F01` then `0x00001001`, then `sleep(2)` | C:794, C:801, C:803 |
| wait GT RX done, toggle GT RX datapath reset | `wait_gt_rxresetdone(4)`, `gt_rx_datapath_reset(4)` | C:807, C:809 |
| link poll | see below | C:812-821 |
| `TICK_REG_0 = 1` | after align, and again after traffic | C:833, C:841 |
| PRBS start/stop | `GENMON_CTL_BASEADDR_LSB = 0x2401` then `0x2400` | C:836-837 |

The MODE_REG value is confirmed by both C and T. FEC is confirmed 0: the
example writes `FEC_CONFIGURATION_REG1_0 = 0` (no RS-FEC, no CL74/Fire FEC),
which is also what the 1x40G Corundum mode must program regardless of
`ETH_RS_FEC_ENABLE`. The T additionally writes `FEC_CONFIGURATION_REG1_[1-3]`
= 0 (T:549-551); these ports are unused here.

Decoded MODE_REG `0x40000A42` (bit positions as in the 4x25G notes):
`ctl_data_rate` [2:0] = 010 (40GE; T:229 comment gives the encoding 10G 000,
25G 001, 40G 010, 50G 011, 100G 100), `ctl_serdes_width` [6:4] = 100,
`ctl_axis_cfg` [11:9] = 101, bit 30 = `tick_reg_mode_sel`. For comparison the
100G value is `0x40000A64` (`ctl_data_rate` 100, serdes width 110, same
`ctl_axis_cfg` and bit 30) in `test_100GE()` (C:548). The serdes-width field
value 100 for 40GE was not cross-checked against PG314 Table 7 here.

### Differences from `test_100GE()` (C:518-634)

- MODE_REG: `0x40000A42` instead of `0x40000A64`.
- GT_LINERATE_RESET: `0x00001F01` / `0x00001001` instead of
  `0x00001F02` / `0x00001002`. The low byte is `gt_line_rate`: 8'h01 for 40G,
  8'h02 for 100G (T:279-284 comments; 4x25GE is also 8'h02). Bit 12 set =
  near-end PCS loopback; the C comment lists 0x...0F01 / 0x...0001 for external.
  (The Near-End PCS value in the C:794 comment, `0x4B001F01`, is an AMD typo
  for 0x1F01.) The gtwiz defines only one rate configuration, LR0, so the
  glue ties `ch_{tx,rx}rate` to 0; the example design drives the rate from
  software.
- PRBS control word `0x2401`/`0x2400` instead of `0x4501`/`0x4500`
  (traffic-generator select, not a MAC register).
- CONFIGURATION_RX/TX_REG1 (0x33 / 0xC03), FEC (0), RESET sequence, TICK, link
  poll and PTP timer writes are the same as `test_100GE()`. The 100G value
  there is also `FEC_CONFIGURATION_REG1_0 = 0` (C:553), so the AMD sample
  never enables RS-FEC even for 100G.
- The T additionally passes `c0_top_ctl_data_rate = 3'b010` and
  `c0_number_of_segments = 3'b100` to the generator (T:574-576); traffic-gen
  controls, not MRMAC registers.

### Link status poll

C:812-821: write `0xFFFFFFFF` to `STAT_RX_STATUS_REG1_0` (clear latched-low),
read it back, mask bits [2:0] and loop until the value equals **0x7**, at most
1000 iterations. Bit 0 `stat_rx_status`, bit 1 `stat_rx_block_lock`, bit 2
`stat_rx_aligned`: all three must be 1 (same as 100G, unlike the 4x25G loop
which compares to 0x3). T waits a fixed delay (200000 `pl_clk` cycles, 45000
with `SIM_SPEED_UP`, T:557-560), clears, reads and checks bit 0 only
(T:564).

### Reset

Per-lane reset-done is `INTF0_rst_{tx,rx}_done_out` replicated to
`{core,serdes}_reset[3:0]` (E:812-815, as in 100G). T reset sequence:
`gt_reset_all_in = 4'hF` for 400 clocks, release, wait
`stat_mst_reset_done[0]`, then the register program (T:505-554).

## Client AXI-Stream word map (256b non-segmented, port 0)

The MRMAC instance exposes `tx/rx_axis_tdata[0-4]` (64b) and
`tx/rx_axis_tkeep_user[0-4]` (11b) plus one `tx/rx_axis_tvalid_0`,
`tx/rx_axis_tlast_0`, `tx_axis_tready_0` (`mrmac_0.v` ports; E:1409-1422,
E:1344-1353). The 40G/50G traffic generator `mrmac_0_core_lbus_pkt_gen_256b`
drives `tx_datain[0-3]` / `tx_mtyin[0-3]`[7:0] (M:535-558), mapped to
`client_tx_axis_tdata[0-3]` / `client_tx_axis_tkeep_user[0-3]` and from there to
the MRMAC `tx_axis_tdata0..3` and `tx_axis_tkeep_user0..3` (E:1893-1908; for
`c0_top_ctl_muxes = 0` the client0 words 2,3 pass straight through, E:1895-1896).
So the 256b port is **tdata/tkeep_user words 0 through 3** (word 0 = bits
[63:0]). The 100G generator additionally uses words 4 and 5 (384b, E:1897-1898),
so for 40G words 4 (and 5) are not driven and the MRMAC word 4 is not part of
port 0. Only tkeep_user[7:0] is used by the generators and by the monitor byte
counters (RX side, M:365-388); bits [10:8] of the 11b tkeep_user are not touched by the
example. RX is the mirror: `rx_axis_tdata0..3` / `rx_axis_tkeep_user0..3`
(E:1854-1869 for the retiming stages).

The extra word 4 (and the 32b PORT2 setting above) is a preset artifact of the
example IP; whether the 1x40G build ties it off was not checked.
