# MRMAC 4x25GE reference (Versal AI Edge, xcve2202)

Reference for the four-independent-port 25GBASE-R configuration of the MRMAC,
captured from the AMD example design generated by Vivado 2025.2. It is the
source for the clocking, reset and register-program work that replaces the
1x100GE implementation (`corundum_vck190_mac.tcl`, `mrmac_versal_glue.v`,
`mrmac_init.v`).

## How the reference was generated

`create_ip -name mrmac` on `xcve2202-sfva784-1MP-i-S` with:

    MRMAC_PRESET_C0 {4x25GE Wide}   MRMAC_MODE_C0 {MAC+PCS}
    MRMAC_IS_GT_WIZ_OLD 0           GT_REF_CLK_FREQ_C0 156.25
    MAC_PORT[0-3]_TX_FLOW_C0 1      MAC_PORT[0-3]_RX_FLOW_C0 1
    MAC_PORT[0-3]_ENABLE_TIME_STAMPING_C0 1

then `generate_target all` and `open_example_project`. Resulting properties
read back from the IP: `GT_TYPE_C0 = GTYP` (forced on this part),
`MAC_PORT[0-3]_RATE_C0 = 25GE`,
`MRMAC_DATA_PATH_INTERFACE_PORT[0-3]_C0 = Independent 64b  Non-Segmented`,
`TIMESTAMP_CLK_PERIOD_NS = 4.0` (250 MHz), `MRMAC_EXDES_GT_LOCATION_C0 =
GTYP_QUAD_X0Y1`, `MRMAC_EXDES_GT_REFCLK_LOCATION_C0 = GTYP_REFCLK_X0Y2`.

Citations below use these example-design files (kept in the generation
scratch area, not in the repo). Names are as generated for the IP name
`mrmac_4x25`:

- `E` = `imports/mrmac_4x25_exdes.sv` (the example wrapper)
- `T` = `imports/mrmac_4x25_exdes_tb.v` (simulation test bench)
- `C` = `mrmac_exdes_test.c` (bare-metal sample, `test_25GE()`)
- `G` = `mrmac_exdes_gt_settings.tcl` (gtwiz_versal configuration)
- `I` = `imports/mrmac_4x25_exdes_imp_top.sv` (board top)

## MRMAC client pins per port

Port n (n = 0..3) uses `tx_axis_tdata{2n}` and `rx_axis_tdata{2n}` (64b),
`tx/rx_axis_tkeep_user{2n}` (11b), `tx/rx_axis_tvalid_n`, `tx/rx_axis_tlast_n`,
`tx_axis_tready_n`, `stat_rx_status_n` (E:508-511 for `tx_axis_tready_n`; E:442
for `stat_rx_status_0`). The example muxes via `mrmac_4x25_axis_stream_mux`
(E:2078-2098); the MRMAC tdata pins are `tx_axis_tdata{0,2,4,6}` (E:1490 for tdata2).
The 25GE AXI-Stream clock is 390.625 MHz (PG314 Table, 25GE, non-segmented,
`ctl_axis_cfg` 3'b001; 322.265 MHz is allowed with `ctl_axis_cfg` 3'b101). The
example uses 390.625 MHz (clk_wiz_0 requested output 390.625, input 100 MHz).

## Clocks

All four ports have their own GT interface and their own MBUFG_GT, no sharing
(the 100G design shares one TX MBUFG_GT across lanes). MBUFG_GT is
`MODE("PERFORMANCE")`, `CE=1`, `CEMASK=0`, `CLRMASK=0`, `DIV=3'b000`, `O3/O4`
open. Per-instance CLR/CLRB_LEAF come from the gtwiz `INTFn_{TX,RX}_clr_out` /
`_clrb_leaf_out` (the example names them `mrmac_0_core_{tx,rx}_clr_out_n` and
`..._clrb_leaf_out_n`).

| MRMAC pin | Port n source | Example line |
|---|---|---|
| `tx_core_clk[n]` | TX MBUFG_GT n **O1** (`MBUFG_GT_tx_usrclk_n`) | E:873-877 via E:1375-1390 |
| `rx_core_clk[n]` | RX MBUFG_GT n **O1** (`MBUFG_GT_rx_usrclk_n`) | E:873, E:1375-1390 |
| `rx_serdes_clk[n]` | RX MBUFG_GT n **O1** (same net as rx_core_clk) | E:874 |
| `tx_alt_serdes_clk[n]` | TX MBUFG_GT n **O2** (`MBUFG_GT_tx_usrclk2_n`) | E:877 |
| `rx_alt_serdes_clk[n]` | RX MBUFG_GT n **O2** (`MBUFG_GT_rx_usrclk2_n`) | E:876 |
| `tx_axi_clk[n]`, `rx_axi_clk[n]` | one 390.625 MHz clk_wiz output (`tx_axi_clk_mmcm`), same net for all 4 ports and both directions | E:866-869, E:892-893 |
| `tx_ts_clk[n]`, `rx_ts_clk[n]` | one 250 MHz clk_wiz output (`ts_clk`), same net for all ports | E:879-880; I:202-205, I:230 |
| `tx_flexif_clk[n]`, `rx_flexif_clk[n]` | tied to `4'b0000` (flex interface unused) | E:840-841 |
| `s_axi_aclk` | `pl0_ref_clk_0` (100 MHz from CIPS), also `gtwiz_freerun_clk` | I:330, E:1549 |

Notes:

- There is no `tx_serdes_clk` pin on the MRMAC in this mode; the
  example does not connect one (E:1393-1543). Same as the 100G glue.
- TX O1/O2 are fed by the TX outclk of GT channel n (`gt_quad_base_chN_txoutclk`,
  E:1737, 1781, 1760, 1801 for N = 0,1,2,3) and RX O1/O2 by the RX outclk of
  channel n (`gt_quad_base_chN_rxoutclk`, E:1827, 1869, 1847, 1888). The
  gtwiz `QUAD0_TXn_usrclk` and `QUAD0_RXn_usrclk` inputs are driven by the **O2**
  outputs (E:1693-1700), identical to the 100G glue (O2 -> gtwiz usrclk and
  alt_serdes, O1 -> core/serdes).
- Frequencies, derived (not read from the example): G sets 25.78125 Gb/s, 80b
  user width and TXPROGDIV/RXPROGDIV 644.531 MHz, so the outclk feeding each
  MBUFG_GT is 644.531 MHz; with DIV = 0 and the O2 tap being a fixed /2 (as the
  100G glue comment states) O1 = 644.531 MHz and O2 = 322.266 MHz. 322.2656 MHz = 25GE Wide GT interface clock
  (PG314 Table 7, `ctl_serdes_width` = b110).
- Reference clock: one `IBUFDS_GTE5` (REFCLK_EN_TX_PATH 0, REFCLK_HROW_CK_SEL 0,
  REFCLK_ICNTL_RX 0), output drives both `QUAD0_GTREFCLK0` and
  `QUAD0_GTREFCLK1` of the gtwiz (E:1899-1912, E:1551-1552). Constraint:
  `create_clock -period 6.400` on `gt_ref_clk_p` (example xdc line 65).
- The example xdc has all MBUFG_GT O1/O2 cross-domain false paths commented out
  (`####set_false_path`, xdc lines 261-286); the pl0 clock is only declared
  asynchronous (xdc line 160).

## Resets

| MRMAC pin | Per-port driver | Example line |
|---|---|---|
| `tx_core_reset[n]` | `~INTFn_rst_tx_done_out` | E:888, E:1370 |
| `tx_serdes_reset[n]` | `~INTFn_rst_tx_done_out` | E:889 |
| `rx_core_reset[n]` | `~INTFn_rst_rx_done_out` | E:886 |
| `rx_serdes_reset[n]` | `~INTFn_rst_rx_done_out` | E:887 |
| `rx_flexif_reset[n]` | `~pl_resetn` (only flexif reset pin that exists) | E:843 |
| `s_axi_aresetn` | `pl0_resetn_0` | I:331 |
| client AXIS resets (`tx/rx_axi_rst`, not MRMAC pins) | `~pl_resetn` for all ports | E:895-896 |
| `ts_rst[n]` (PTP timer blocks only) | `~pl0_resetn_0` | I:231 |

- Each port's GT reset-done is per interface: `INTFn_rst_tx_done_out` and
  `INTFn_rst_rx_done_out` of its own gtwiz interface. This differs from the 100G
  design, where one interface `INTF0_rst_{tx,rx}_done_out` drives all four lanes
  of every `mrmac_*_reset[3:0]`.
- gtwiz reset inputs per interface (E:1592-1598 for n=0, same pattern for 1-3
  at E:1628-1634, 1656-1662, 1682-1688):
  `INTFn_rst_all_in = gt_reset_all_in[n]` (driven from the CIPS block in the
  example, I:524, so the example holds each interface independently),
  `INTFn_rst_tx_datapath_in = gt_reset_tx_datapath_in[n]`,
  `INTFn_rst_rx_datapath_in = gt_reset_rx_datapath_in[n]`,
  `INTFn_rst_{tx,rx}_pll_and_datapath_in = 1'b0`.
- `QUAD0_s_axi_lite_resetn` = `s_axi_aresetn` (E:1554).
- Test bench reset sequence (T:671-700, the "double reset" analogue):
  `gt_reset_all_in = 0`, wait `stat_mst_reset_done[0]` (= `gt_rx_reset_done_out`
  E:2864), 400 clocks, then `pl_resetn = 0` and `gt_reset_all_in = 4'hF` for 400
  clocks, release both, wait `|stat_mst_reset_done`, 400 clocks, then the
  register program (T:778-819). C: `MRMAC_0_GT_LINERATE_RESET = 0x00071F00` then
  `0x00071000` (C:984, C:991). The register is an AXI GPIO in the example CIPS
  block that is sliced into the GT control pins (CIPS BD slices
  `xlslice_gt_reset` DIN [11:8] -> `gt_reset_all_in[3:0]`, `xlslice_line_rate`
  DIN [7:0] -> `gt_line_rate`, `xlslice_gt_loopback` DIN [14:12] ->
  `gt_loopback`; read from `mrmac_4x25_cips.bd`). The `[8:1] gt_line_rate`
  in the C comments (C:681, 799, 988) overlaps `[11:8]` and is an AMD comment
  typo (C:564 says `[7:0]`); the BD slice is authoritative. In the written
  values bit 12 is set, i.e. `gt_loopback` = 3'b001 (near-end PCS loopback; the
  C comment lists 0x00070F02 / 0x00070002 as the external-loopback values with
  bit 12 clear), so the C sample runs the example in near-end PCS loopback.
  Bits [18:16] = 7 are not consumed by any of the GT slices listed above
  (purpose not determined). Per-interface datapath resets come from a
  separate debug GPIO (`MRMAC_0_GT_DATAPATH_RESET`, C:267): `xlslice_gt_reset_tx_datapath`
  [3:0] -> `gt_reset_tx_datapath_in`, `xlslice_gt_reset_rx_datapath` [7:4] ->
  `gt_reset_rx_datapath_in`.
- `gt_line_rate` is 8'h00 in the T (T:569) and the C writes replicated per interface into
  `INTFn_TX0_ch_txrate` and `INTFn_RX0_ch_rxrate` (E:1304, E:1585 for n=0:
  `SW_REG_GT_LINE_RATE[8n+7:8n]`). The 100G design ties gt_line_rate to a constant too.
- `gt_loopback` is one 3-bit value fanned to `QUAD0_ch0..3_loopback`
  (E:1599-1602).

## Per-port MRMAC register program

Register block stride between ports is **0x1000** (port n at base `n * 0x1000`;
T:59-142, C:55-138). All offsets are within the MRMAC AXI4-Lite space.

| Register | Port 0 | Port 1 | Port 2 | Port 3 | Value written (4x25GE) | 1x100GE (`mrmac_init.v`) |
|---|---|---|---|---|---|---|
| RESET_REG | 0x0004 | 0x1004 | 0x2004 | 0x3004 | 0xFFF (T:779-782), 0xFFFFFFFF (C:939-942) assert; 0 release (T:811-815, C:977-980) | 0x0004 |
| MODE_REG | 0x0008 | 0x1008 | 0x2008 | 0x3008 | 0x40000261 (T:785-801, C:946-971) | 0x40000a64 |
| CONFIGURATION_TX_REG1 | 0x000C | 0x100C | 0x200C | 0x300C | 0x00000C03 (T:789-804) | 0x00000c02 |
| CONFIGURATION_RX_REG1 | 0x0010 | 0x1010 | 0x2010 | 0x3010 | 0x00000033 (T:788-803) | 0x00000032 |
| FEC_CONFIGURATION_REG1 | 0x00D0 | 0x10D0 | 0x20D0 | 0x30D0 | 0x00000000 (T:806-809, C:952-975) | 0x1008 (RS FEC on) |
| TICK_REG | 0x002C | 0x102C | 0x202C | 0x302C | 0x1 (T:816-819, 907-910) | 0x002c |
| STAT_RX_STATUS_REG1 | 0x0744 | 0x1744 | 0x2744 | 0x3744 | write 0xFFFFFFFF (clear) then read (T:828-860, C:1005-1010) | 0x074c (`ADDR_RT_STAT`) |

Order in the example (T:779-819, C:939-980): assert RESET_REG on all four ports;
for each port write MODE, CONFIGURATION_RX, CONFIGURATION_TX; write
FEC_CONFIGURATION on each port; release RESET_REG (written twice for port 0 in
T:811-812); write TICK_REG = 1 on each port; wait for alignment. In C the
order is RESET all, then per port MODE / RX / TX / FEC, then RESET release; no
TICK before the wait.

Decoded values (register map from `mrmac-registers-v3-1.xlsx`, field meanings
from PG314 v3.1):

- MODE_REG `0x40000261`: `ctl_data_rate` [2:0] = 001 (25GE; Table 3 allows 001
  for ports 0..3), `ctl_serdes_width` [6:4] = 110 (25GE Wide, 80b, Table 7),
  `ctl_axis_cfg` [11:9] = 001 (25GE, 390.625 MHz AXI clock, non-segmented),
  bit 30 = `tick_reg_mode_sel` (xlsx MODE_REG_0 row `C=30`; tick from the
  TICK_REG rather than the `pm_tick` pin; the example ties `pm_tick` to 0,
  E:533). The 100G value `0x40000a64` has data rate 100, same serdes width,
  `ctl_axis_cfg` 101 (100GE 390.625 MHz non-segmented) and the same bit 30.
- CONFIGURATION_TX_REG1 `0x00000C03`: bit 0 `ctl_tx_enable`, bit 1
  `ctl_tx_fcs_ins_enable`, [11:8] `ctl_tx_ipg_value` = 0xC. Differs from 100G
  (0x0c02) only in bit 0: the 100G sequencer holds enable low and mirrors the
  Corundum tx enable into bit 0 later.
- CONFIGURATION_RX_REG1 `0x00000033`: bit 0 `ctl_rx_enable`, bit 1
  `ctl_rx_delete_fcs`, bits 4/5 `ctl_rx_check_sfd` / `ctl_rx_check_preamble`.
  Same as 100G (0x32) plus the enable bit.
- FEC_CONFIGURATION_REG1 `0` (the example, FEC disabled). Field layout from the
  xlsx (FEC_CONFIGURATION_REG1_0, 0x00D0): [3:0] `ctl_fec_mode`, 4
  `ctl_rx_fec_bypass_indication`, 5 `ctl_rx_fec_bypass_correction`, 6
  `ctl_rx_fec_transcode_clause49` (1 for 25GE/50GE/FC, 0 for 100GE which uses
  Clause 82 transcoding), 7 `ctl_rx_fec_alignment_bypass`, 8
  `ctl_tx_fec_transcode_bypass`, 9 `ctl_rx_fec_transcode_bypass`, 10
  `ctl_rx_fec_cdc_bypass`, 11 `ctl_rx_fec_errind_mode`, 12
  `ctl_tx_fec_four_lane_pmd` (1 for 100GAUI-4/CAUI-4 with RS-FEC, 0 otherwise).
  Decode of the 100G value in `mrmac_init.v`: `0x1008` = bit 12 (four-lane PMD)
  + `ctl_fec_mode` 0b1000 (IEEE 802.3 RS(528,514)); bit 6 is 0 (Clause 82).
  25GE modes (PG314 Table 6): 0b0010 25G/50G Consortium RS(528,514); 0b0011
  IEEE 802.3 CL108 RS(528,514); 0b1110 CL74 (Fire); 0b0000 disabled.
  **RS-FEC enable recipe for 25GE Clause 108, per port:
  `FEC_CONFIGURATION_REG1_n = 0x00000043`** (bit 6 `transcode_clause49` + mode
  0b0011; 0x00000042 for the Consortium RS(528,514) variant; bit 12 stays 0).
  How this was established: the example was regenerated with
  `MRMAC_MODE_C0 {MAC+PCS+FEC}` and
  `FEC_SLICE[0-3]_CFG_C0 {25G (IEEE 802.3 CL108)- RS(528 514)}` (valid values
  for the slice option are Consortium RS(528 514), CL108 RS(528 514), CL74
  Fire(2112 2080) and FEC Disabled (Bypass); the option only exists in
  MAC+PCS+FEC mode). The generated `mrmac_4x25_wrapper.v` then differs from the
  no-FEC one only by: `NUM_25G_MAC_PCS_WITH_FEC_PORTS = 4` (was 0, NOFEC 4 ->
  0), `CTL_FEC_MODE_n = 4'b0011` (was 0), `CTL_RX_FEC_TRANSCODE_CLAUSE49_n =
  "TRUE"` (was FALSE), the 50G VL length params (0x4FFF vs 0x3FFF, 50G only,
  ports 0 and 2), and extra FEC status ports (`stat_rx_fec_aligned_n`,
  `stat_rx01/23_fec_degraded_ser`). All other FEC bypass/errind/PMD parameters
  are FALSE, so the register power-up value with FEC on is bits 6 and
  [3:0] = 0x43. **The example's register program does not change**: the
  regenerated T and C still write `FEC_CONFIGURATION_REG1_n = 0` (T:806-809,
  C:951-974), which would switch FEC back off and clear bit 6. So a design
  using the FEC build must write 0x43 (or skip the write), not copy the 0.
  No other register has to change for FEC: MODE_REG stays 0x40000261 (same
  data rate, serdes width 110 and `ctl_axis_cfg`), CONFIGURATION_TX/RX unchanged
  (0xC03 / 0x33); the FEC mode is applied by the reset that follows the write
  (PG314: a change to FEC_CONFIGURATION_REG1 needs a port reset). Optional,
  default 0: CONFIGURATION_TX bit `ctl_tx_ptp_rsfec_comp_en` (timestamp
  compensation when RS-FEC is active). Differences from the 100G sequencer:
  bit 12 stays 0, mode 0b0011 not 0b1000, bit 6 set.
- Link status registers (xlsx rows STAT_RX_STATUS_REG1_n, STAT_RX_FEC_*): per
  port at `0x744 + n*0x1000` (`STAT_RX_STATUS_REG1_n`, latched-low W1C, so
  write 0xFFFFFFFF then read): bit 0 `stat_rx_status` (PCS aligned and not
  hi_ber), bit 1 `stat_rx_block_lock`, bit 2 `stat_rx_aligned` (all lanes
  aligned), bit 3 misaligned, 4 aligned_err, 5 hi_ber, 6 remote_fault, 7
  local_fault, 8 internal_local_fault. The real-time (non-latched) copy is
  `STAT_RX_RT_STATUS_REG1_n` at `0x74C + n*0x1000`. The C sample clears,
  reads, masks bits [2:0] and loops until the value equals 0x3, i.e.
  bit 0 (`stat_rx_status`) = 1, bit 1 (`stat_rx_block_lock`) = 1 and bit 2
  (`stat_rx_aligned`) = 0 (C:1005-1010, at most 1000 iterations); for 100G it waits for 0x7 (C:587), so
  the 25G loop requires bit 2 to be 0 rather than 1. T waits
  200000 `pl_clk` cycles (12500 with `SIM_SPEED_UP`, T:826), clears and reads
  and checks bit 0 only (T:828-860).
- RS-FEC lock/alignment (only with the FEC build): `STAT_RX_FEC_STATUS_REG_n`
  at `0x784 + n*0x1000` (latched, W1C, clear then read): bit 0
  `stat_rx_fec_aligned` (FEC aligned/deskewed, ready for data), bit 1
  `stat_rx_fec_hi_ser` (symbol-error threshold K = 417 exceeded in an 8192
  codeword window), bits [7:4] `stat_rx_fec_lane_lock` (lane lock per FEC
  lane; a 25GE slice has one lane, so only the lowest bit is expected to be
  meaningful, not verified). Real-time copy `STAT_RX_FEC_RT_STATUS_REG_n` at
  `0x788 + n*0x1000`; TX side `STAT_TX_FEC_STATUS_REG_n` `0x798` (bit 0 lane
  align, [5:1] block lock, [10:6] AM lock). For the link-up check with FEC on:
  `stat_rx_fec_aligned` (0x784/0x788 bit 0) must be 1 together with
  `stat_rx_status` and `stat_rx_block_lock` (0x744/0x74C bits 0 and 1). The
  FEC-aligned condition feeding bits 0/1 of STAT_RX_STATUS was not checked in
  hardware or simulation; the combined check is a recommendation, not an
  example behaviour.
- Flow control: the example does not write any pause/flow-control registers
  (`TX_FC`, `RX_FC`) for 4x25GE, only the five registers above. Offsets
  confirmed from the xlsx register map: port 0 `CONFIGURATION_TX_FLOW_CONTROL_
  REFRESH_REG1_0` = 0x004C, `CONFIGURATION_RX_FLOW_CONTROL_REG1_0` = 0x009C,
  `CONFIGURATION_RX_FLOW_CONTROL_REG2_0` = 0x00A0; the same registers for
  ports 1, 2, 3 are 0x104C/0x109C/0x10A0, 0x204C/0x209C/0x20A0 and
  0x304C/0x309C/0x30A0 (all listed in the xlsx), i.e. stride 0x1000 per port, as
  for every other per-port register (also STAT_RX_FEC_STATUS_REG_n 0x0784,
  0x1784, 0x2784, 0x3784). These match `ADDR_TX_FC`, `ADDR_RX_FC1`,
  `ADDR_RX_FC2` in `mrmac_init.v`; values for 25GE are not shown by the
  example, so reuse the `mrmac_init.v` values per port.
- PTP timer blocks (separate AXI4-Lite peripherals `ptp_n_s_axi`, 0xA4A00000,
  0xA4B00000, 0xA4C00000, 0xA4D00000, stride 0x100000; T:705-772, C:884-935)
  are not part of the MRMAC register space; each is written with 0x00 -> 0x00010011
  (C writes 0x00000011), 0x18 <- 0x33333333, 0x10 <- 0x99, 0x14 <- 0xAA,
  0x208 <- 0, 0x20C <- 0x40000, 0x228 <- 0, 0x22C <- 0x40000, 0x28/0x2C/0x30 <-
  0, 0x1C <- 3. They belong to the AMD test timer IP, not to the MRMAC.

## Differences from the 1x100GE implementation

| Item | 1x100GE (existing) | 4x25GE (example) |
|---|---|---|
| mrmac preset / data path | `1x100GE CAUI-4 Wide`, `Independent 384b Non-Segmented` | `4x25GE Wide`, `Independent 64b  Non-Segmented` x4 |
| Client interface | one 384b AXIS on port 0 | four 64b AXIS, `tdata{2n}` / `tkeep_user{2n}` (11b) |
